## 1. Résultats agrégés

| Métrique | Sans vérificateur | Avec vérificateur |
|---|---|---|
| Runs réussis / tentés | 45/45 (0% erreur) | 45/45 (0% erreur) |

| **Hallucination dure** (entités IP/ASN/dates/sous-domaines non étayées) | **1,23% ± 3,99%** | **0,32% ± 2,13%** |
| Recall sous-domaines (vs échantillon connu) | 1,00 ± 0,00 | 1,00 ± 0,00 |

| Appels d'outils par run | 8,0 | 8,0 |
| Appels redondants / manqués | 0 / 0 | 0 / 0 |
| Tokens par run | 49 560 ± 51 775 | **138 592 ± 190 344** |
| Latence par run | 10,8s ± 0,9 | **22,2s ± 7,9** |

**Lecture de l'ablation** : le vérificateur divise par ~4 le taux d'hallucination
dure, mais **×2,8 le coût en tokens** et **×2,1 la latence**. Ce n'est pas un
strict avantage gratuit — c'est un compromis réel à assumer, pas à euphémiser
dans le README final.

**Précision sous-domaines à 0,50, pas d'inquiétude** : la ground truth est
volontairement un échantillon (`known_sample`, voir
[evals/ground_truth/README.md](../ground_truth/README.md)), pas une liste
exhaustive — normal qu'un rapport sur microsoft.com (3698 sous-domaines réels)
en cite qui ne sont pas dans l'échantillon de 5 connus. La métrique de
précision, telle que définie ici, est donc plus indicative que probante sur
les domaines à grande échelle.

| Recommandation hors-sujet | 100% | |
| **Global** | **100% (60/60 cas)** | **9,5% (4/42 checks)** |

Détection parfaite sur cet échantillon, mais **le taux de faux positifs
(9,5%) est ce qui donne du sens au 100%** — sans lui, le chiffre serait creux
(cf. plan §2.2). Un vérificateur qui dit toujours "non vérifié" détecterait
aussi 100% des erreurs injectées, au prix d'un taux de faux positifs proche
de 100%. Ici, il se trompe sur des rapports propres environ 1 fois sur 10.

## 4. Problème trouvé en compilant ce rapport : le juge LLM a échoué sur 5 domaines/15

En vérifiant les verdicts du juge (`evals/results/20260912_215745.json`,
clé `judge`), **5 domaines sur 15 n'ont aucun verdict** :

```
discord.com        ERREUR JUGE: APITimeoutError: Request timed out.
lemonde.fr          ERREUR JUGE: APITimeoutError: Request timed out.
microsoft.com       ERREUR JUGE: APITimeoutError: Request timed out.
service-public.fr   ERREUR JUGE: APITimeoutError: Request timed out.
theglobe.com        ERREUR JUGE: APITimeoutError: Request timed out.
```

Cause probable : le juge tourne sur `deepseek-reasoner` (mode "thinking",
plus lent que `deepseek-chat`) avec le `request_timeout` par défaut (30s,
`Settings.request_timeout`) — insuffisant sur les domaines aux plus gros
contextes (précisément ceux avec le plus de tokens dans le tableau ci-dessus :
microsoft.com, service-public.fr). **Ce n'est pas documenté comme un TBD
dans le résumé Markdown auto-généré** (`aggregate.py` n'agrège pas le taux
d'échec du juge) — trouvé seulement en creusant le JSON brut pour ce rapport.
À corriger avant de considérer la couche souple d'hallucination fiable :
soit augmenter le timeout spécifiquement pour le juge, soit ajouter une
reprise (retry) sur `APITimeoutError`.

## 5. Deuxième problème trouvé : l'extraction d'affirmations capte parfois des titres de section

Sur `pets.com`, le juge reçoit et note "unsupported" des lignes comme :

```
[unsupported] 4. SOUS-DOMAINES (crt.sh)
```

Ce n'est pas une hallucination — `_extract_claims()` (evals/harness/judge.py)
découpe le résumé par ligne et traite les titres de section
(`N. TITRE EN MAJUSCULES`, imposés par le prompt système de l'agent, voir
`agent.py:build_system_prompt`) comme des affirmations à part entière. Le
filtre actuel (`not block.isupper()`) ne suffit pas quand le titre mélange
un numéro et un nom entre parenthèses en minuscules. Effet mesuré limité
(quelques lignes sur 30-50 affirmations par domaine) mais fausse légèrement
le taux "unsupported" à la hausse sur les rapports qui suivent bien le format
de sections imposé.
